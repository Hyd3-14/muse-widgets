詰みの連鎖と、どこで切れたか
① 10/26、daemon が死ぬ際に 0バイトの daemon-v52.pid が残った
② 以後の daemon 起動は全て EEXIST で Fatal 終了（pid ファイルが既にある）
③ orcad は失敗を掴んだまま再試行せず、census は unverifiable の一言で stderr を隠した
④ 更新ガードが protocol 不明を理由に永久に延期 → 新版は毎日DLされるだけ
切れた場所：stale な pid と socket を削除 → WSL再起動で daemon が ready → census 正常化 → forceなしで更新完了
根本対策の3層
本命 upstream 修正：中身が空で所有プロセスもいない pid ファイルを stale と判定して消す処理が daemon に無い。census が daemon の stderr を出すことも含め、Issue にする価値がある
運用 版遅れを溜めない：今回は 1.4.241→1.4.267 の26版遅れで protocol が v52→v61 に drift した。ターミナルを閉じて更新する窓を定期的に作る
検知 死活チェック：pid ファイルがあるのに socket が接続拒否なら stale、という判定は今回の形そのまま自動化できる（対策ではなく早期発見）
