MVP 範囲グリル · ラウンド1（土台の6問）

前提は確定済みとして置く — 本体は「quota 結合＋診断」の層、最初のユーザーは tantan 本人、集計は既存ツールが強い。依存する詳細（診断レンズの取捨、閾値、名前と配布）はラウンド2へ回す。

Q1. プロダクトの形
  • 結合レイヤー特化：ccusage の JSON を入力に、quota 結合と追加診断だけを作る推奨
  • 単体フルスタック：アダプタから全部自前
  • agent-audit のフォーク拡張
理由：形式追随の保守を ccusage に肩代わりさせ、新規性に全振りできる。ステップ単位の診断が要る部分だけ自前パースを持つ
Q2. MVP の対応ハーネス
  • agy ＋ Claude Code の2つ推奨
  • agy のみ
  • agy ＋ Claude Code ＋ Codex の3つ
理由：agy が新規性の核で外せない。Claude Code は JSONL で易しく市場が最大。Codex は既存2ツールが強く、差が出しにくいので後回し
Q3. quota 結合の MVP 範囲
  • agy の quota 履歴だけ（履歴ファイルの形式を仕様として定義し、自分の rate-collector を最初の実装例にする）推奨
  • Claude の quota も最初から
  • quota 結合は MVP 外（診断のみで出す）
理由：実証済みなのは agy の経路だけ。Claude quota は取得経路が別で、足すと MVP が膨らむ
Q4. 言語
  • Go推奨
  • Rust
理由：個人開発の速度、単一バイナリ、将来 TUI を足すときの道具の揃い方。Rust の看板効果より、早く出して反応を見る方が今は大事
Q5. 出力形式
  • CLI レポート（Markdown）＋ JSON 出力推奨
  • レポートのみ
  • 最初から TUI ダッシュボード
理由：JSON があると自分の pace 生成や他ツール連携に使える。TUI は見せ場だが MVP の本体じゃない
Q6. 公開の進め方
  • 自分用に作って 2 週間 dogfooding → public 公開推奨
  • 最初から public で開発
  • 公開せず自分用で止める
理由：昨日のような実データの事故・急騰を自分の環境で踏んでから出すと、README に書ける実例が揃う
