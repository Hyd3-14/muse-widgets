MVP 範囲グリル · ラウンド2（中身の6問）

ラウンド1は全て推奨どおりで確定し、決定ログに記録済み。ラウンド2は診断の中身と結合の方式。

Q7. 診断レンズの取捨
  • 実証済み3レンズ（キャッシュ破壊／全文読み＋重複読み／サブエージェント散らかり）＋急騰区間の犯人特定推奨
  • キャッシュ破壊だけに絞る
  • 3レンズ＋フェーズ分解（探索 vs 実装）まで全部入り
理由：3レンズは agent-audit の実データで全部実際に引っかかった。フェーズ分解は面白いが判定が主観寄りで、MVP の説明コストが高い
Q8. quota とセッションの突き合わせ方式
  • 時間窓で按分：quota が増えた区間に活動していたセッションへ、uncached 量の比でポイントを配り「推定」と明記する推奨
  • 按分せず、急騰区間のセッション一覧を候補として出すだけ
  • 並列表示のみ（結合しない）
理由：按分は推定だが「枠の何%を誰が食ったか」という一番欲しい数字が出る。推定であることを数字の横に必ず書く
Q9. bot・タスクの識別
  • ワークスペースとブランチ名から引く（例：feat/414-… → Issue #414）。決定的に取れる信号を主キーにする推奨
  • Orca の bot 一覧と突き合わせて bot 名まで出す
  • MVP ではセッション単位まで（bot・タスク単位はやらない）
理由：ブランチ名は昨日のログでも安定して取れた。bot 名の対応表は Orca 側の状態に依存して壊れやすいので次段に回す
Q10. 異常検知の閾値
  • 固定閾値：15分で +20pt 以上を急騰とする（昨日の +33.6pt/17分 が拾える水準）推奨
  • 移動平均からの乖離で判定する（統計方式）
  • 検知はせず、急騰区間のランキング表示だけ
理由：固定なら「なぜフラグが立ったか」を1行で説明できる。統計方式はデータが貯まってからでも足せる
Q11. pace（B＋C）との統合
  • この OSS の JSON 出力を pace 生成が使う。pace は別プロジェクトのまま、OSS はその入力部品になる推奨
  • OSS に pace 出力まで内蔵する
  • 統合しない（別々に作る）
理由：pace は自分の環境専用の配線で、OSS は汎用品。JSON で疎結合にすると両方壊れにくい
Q12. 名前と配布
  • 名前は仮名で開発し、公開前に決める。配布は GitHub Releases の単一バイナリのみ推奨
  • 名前を今決める（候補を別途出す）
  • 配布に Homebrew tap まで最初から含める
理由：名前で止まるのが一番もったいない。brew は公開後の反応を見てからで間に合う

このラウンドで MVP が閉じる

確定したら、決定ログを完成させて MVP の仕様書（入力形式・レポート構成・按分の計算式）に落とす。実装着手はその次の判断。
