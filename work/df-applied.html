df の規則を VM に当てるとどうなるか
今の VM
df 流儀を当てた姿
リポの clone
workspace 直下に散在。dotfiles 自身が5つある（dotfiles-vm、df-297-work、agent-launch、registry-work、skills-check）
ghq の root（~/repo）に github.com/owner/repo の形で一元化。1つの repo は1か所だけ
並列の作業場
タスクごとに full clone を切って捨て忘れる（cram 系 32件・9.0GB）
gwq の worktree で ~/worktrees/host/owner/repo/branch に配置。ブランチ名も type/Issue番号-概要 の形で規則化
一時作業
置き場の決めがなく、workspace 直下に残り続ける
~/agent-tmp に寄せ、MANIFEST に expires を書く。期限切れと7日無更新は .trash へ移り、さらに7日で消える（毎日 prune）
終了処理
なし。終わったかどうかは記憶頼み
gprune-merged が merge 済みを安全条件つきで一括整理。週1回、削除なしの棚卸しレポート（worktree-report）も回る
ツール
実体がツールごとにバラバラで、.bin へ symlink を手で集約。版の管理も個別
mise で一元管理し、版は lock で固定。gwq も ghq も mise 管理で、他の手段と重複させない原則まである
Muse 固有の層
goals、your_files、ts-spaces、MEMORY など
df の対象外なので残る。ただし expires と .trash の考え方は、この層の作業フォルダにも流用できる
根拠は df の docs/gwq-worktrees.md と docs/agent-tmp.md。df 側の仕組みは WSL2 と lab-arch の端末前提で組まれていて、VM が df の配置対象に入っているかは未確認。
